1) Qué métricas necesitas
A nivel RAG moderno se suelen medir tres ejes clave (lo que llaman el “RAG triad” o similares):

Context relevance / precision: qué bien se ajusta el contexto recuperado a la pregunta, sin ruido.

Context sufficiency / recall: si el contexto recuperado contiene toda la info necesaria para responder bien.

Answer faithfulness (alucinaciones): si la respuesta se apoya solo en el contexto o “se inventa cosas”.

En tu plataforma esto se puede mapear a:

contextprecision ≈ qué parte del contexto es realmente relevante.

faithfulness ≈ qué porción de la respuesta está soportada por el contexto (baja alucinación).

answerrelevance ≈ si la respuesta contesta a la query del usuario.

Tu RagJudgeService ya devuelve algo muy parecido (faithfulness, answerrelevance, contextprecision).
​

2) Aprovechar tu RagJudgeService (LLM-as-a-judge)
La literatura reciente confirma que usar un LLM como “juez” bien diseñado es de lo más correlacionado con humanos para evaluar faithfulness y alucinaciones.

En tu código:

RagJudgeService.evaluateResponse(query, context, response, industry, tenantId, correlationId?) ya hace exactamente esto: llama a un prompt RAGJUDGE y devuelve métricas.
​

Campos clave del resultado: metrics.faithfulness, metrics.answerrelevance, metrics.contextprecision, más feedback y causalanalysis (para explicar el fallo).
​

Con esto puedes:

Evaluar offline un lote de queries “golden” para comparar RAG v1 vs v2.

Evaluar online una muestra de tráfico real (p.ej. 5–10% de las respuestas) y sacar un “Hallucination score” por tenant/industria en tu dashboard.

3) Definir un “Hallucination Score” de plataforma
Puedes derivar un indicador simple a partir de faithfulness:

A nivel respuesta:

hallucinationScore = 1 - faithfulness (normalizado 0–1).

A nivel tenant/industria:

Promedio de hallucinationScore sobre una ventana de tiempo (p.ej. 7 o 30 días).

Mostrarlo ya en tu UI donde tienes “Hallucination Score” y “RAG faithfulness” en el panel de Observability.
​
​

Umbrales típicos:

faithfulness >= 0.8 → “verde / confiable”.

0.6–0.8 → “amarillo / revisar en casos críticos”.

< 0.6 → “rojo / alto riesgo de alucinación”.

Esto te da una forma tangible de decirle a un COO “el nuevo engine reduce el porcentaje de respuestas con riesgo de alucinación desde X % a Y %”.

4) Inserción desde RagJudgeService
En tu RagJudgeService.evaluateResponse, tras obtener evaluation, añades algo como:
​

ts
import { getTenantCollection } from 'lib/db-tenant';

export class RagJudgeService {
  static async evaluateResponse(
    query: string,
    context: string,
    response: string,
    industry: string,
    tenantId: string,
    correlationId?: string,
    extra?: {
      contextChunks?: {
        assetId: string;
        sectionId?: string;
        chunkId?: string;
        source?: string;
        text?: string;
      }[];
      flowType?: string;
      flowId?: string;
      modelUsed?: string;
      ragEngineVersion?: number;
    },
  ): Promise<RagEvaluationResult> {
    const cid = correlationId ?? `judge-${Date.now()}`;

    const evaluation = await PromptRunner.runJson(/* prompt RAGJUDGE */, {
      query,
      context,
      response,
      vertical: industry,
    }, tenantId, cid);

    const doc = {
      tenantId,
      industry,
      correlationId: cid,
      query,
      response,
      contextChunks: extra?.contextChunks ?? [],
      metrics: {
        faithfulness: evaluation.faithfulness,
        answerrelevance: evaluation.answerrelevance,
        contextprecision: evaluation.contextprecision,
        hallucinationScore: 1 - evaluation.faithfulness,
      },
      judgemodel: 'gemini-2.5-pro', // o el que toque
      reasoning: evaluation.reasoning,
      causalanalysis: evaluation.causalanalysis,
      flowType: extra?.flowType ?? 'UNKNOWN',
      flowId: extra?.flowId,
      modelUsed: extra?.modelUsed,
      ragEngineVersion: extra?.ragEngineVersion ?? 2,
      timestamp: new Date(),
    };

    const collection = await getTenantCollection('rag_evaluations');
    await collection.insertOne(doc);

    return {
      tenantId,
      correlationId: cid,
      query,
      generation: response,
      contextchunks: context,
      metrics: {
        faithfulness: evaluation.faithfulness,
        answerrelevance: evaluation.answerrelevance,
        contextprecision: evaluation.contextprecision,
      },
      judgemodel: 'gemini-2.5-pro',
      feedback: evaluation.reasoning,
      causalanalysis: evaluation.causalanalysis,
      timestamp: new Date(),
    };
  }
}

2) Estrategia de muestreo de tráfico
La idea: evaluar solo una fracción de respuestas, suficiente para tener métricas estables pero sin disparar coste.

a) Muestreo aleatorio simple por respuesta
Por ejemplo, p = 0.05 (5% de las respuestas).

En el punto donde generas la respuesta (assistant / workflow / agente):

tiras un random,

si Math.random() < p, llamas a RagJudgeService.evaluateResponse.

Ventajas:

Implementación trivial.

Representativo si el tráfico no está muy sesgado.

b) Muestreo estratificado por flowType
Para no quedarte solo con assistant y olvidarte de workflows/agentes:

Definir una probabilidad por tipo:

TECHNICAL_ASSISTANT: 5–10%.

AGENT_MAINTENANCE: 20% (más crítico).

WORKFLOW_NODE: 5%.

Pseudocódigo:

ts
const samplingRates: Record<string, number> = {
  TECHNICAL_ASSISTANT: 0.05,
  AGENT_MAINTENANCE: 0.2,
  WORKFLOW_NODE: 0.05,
};

const rate = samplingRates[flowType] ?? 0.05;

if (Math.random() < rate) {
  await RagJudgeService.evaluateResponse(query, context, response, industry, tenantId, correlationId, extraMeta);
}
c) Muestreo dirigido por riesgo
Una vez tengas métricas:

Aumentar la probabilidad de muestreo cuando:

flowType/flowId tienen faithfulness_mean bajo o red_ratio alto.

También puedes forzar evaluación al 100% para:

nuevos flows,

cambios recientes de modelo/prompt (durante unos días).

Helper para decidir si evaluar
ts
// lib/eval-sampling.ts
import { DEFAULT_SAMPLING_CONFIG } from '../config/sampling-defaults';
import type { FlowType, SamplingConfig } from '../types/sampling';

export function shouldSampleEvaluation(
  flowType: FlowType,
  flowId: string | undefined,
  tenantConfig?: Partial<SamplingConfig>,
): boolean {
  const cfg: SamplingConfig = {
    ...DEFAULT_SAMPLING_CONFIG,
    ...tenantConfig,
    perFlowType: {
      ...DEFAULT_SAMPLING_CONFIG.perFlowType,
      ...(tenantConfig?.perFlowType ?? {}),
    },
    overrides: tenantConfig?.overrides ?? DEFAULT_SAMPLING_CONFIG.overrides,
  };

  if (!cfg.enabled) return false;

  // 1) Buscar override activo
  const now = new Date();
  const override = cfg.overrides.find((o) => {
    if (o.flowType !== flowType) return false;
    if (flowId && o.flowId !== flowId) return false;
    if (o.until && new Date(o.until) < now) return false;
    return true;
  });

  const rate =
    override?.rate ??
    cfg.perFlowType[flowType] ??
    cfg.defaultRate;

  if (rate <= 0) return false;
  if (rate >= 1) return true;

  return Math.random() < rate;
}

Para cerrar el bloque que tenías planificado, vamos ahora con el impacto en coste/tokens por documento y límites razonables en este diseño jerárquico.

1) Dónde gastas tokens y cuota
En el pipeline jerárquico, los principales costes son:

Resúmenes de secciones (LLM barato).

Resumen global (LLM).

Embeddings de summaryGlobal y summaries de sección.

El uso en generación (chat/agents) no cambia mucho respecto a tu RAG actual; lo que cambia de verdad es la ingest.

2) Orden de magnitud por documento
Supón un manual de 50–80 páginas que, tras segmentar, produce:

15–25 secciones útiles.

Resumen de cada sección ~200–300 tokens de salida, ~800–1.200 tokens de entrada (depende de cómo trocees).

Aproximación razonable:

20 secciones × (entrada 800 + salida 250) ≈ 21.000 tokens LLM por doc.

Resumen global: entrada con todos los summaries (recortados) ~2.000 tokens, salida ~500 → 2.500 tokens.

Total por doc (resúmenes): ~23.500 tokens LLM.
Embeddings:

20 summaries + 1 global = 21 embeddings.

Si usas un modelo tipo Gemini embeddings, el coste es muy bajo comparado con LLM de generación, pero suman si embebes millones de docs.
​

En la práctica, con un modelo “flash/mini” y precios actuales, esto suele estar en el orden de centésimas de dólar por doc grande. El truco es no multiplicarlo por chunks innecesarios.

3) Límites razonables por documento
Para controlar coste y no pasarte:

Máximo secciones por documento

Cap: 30 secciones. Si el doc es muy largo, fusionar secciones o elevar nivel (p.ej. solo H1/H2 significativos).

Máximo tokens de entrada por resumen de sección

Trocear cada sección en bloques de 800–1.000 tokens y pedir un solo resumen por sección (no por sub‑chunk).

Si una sección es descomunal, considerar dividirla en secciones lógicas adicionales y no en un resumen de 8k tokens.

Máximo tokens de entrada para resumen global

Antes de pasarlo al LLM, recortar cada summary de sección a p.ej. 150 tokens y limitar a 20–25 secciones → ≤3.750 tokens de entrada.

Embeddings

Solo embeder summaries y global, no todo el texto;

asegurar que la longitud de cada summary entra en el “sweet spot” del modelo de embeddings (no más de 512–1.024 tokens).

Con eso, un doc “normal” se queda en algo manejable (≈25k tokens LLM y 20–30 embeddings).

4) Estrategia de control de coste
Puedes aprovechar lo que ya tienes (LLMCostTracker, UsageService, etc.) para:

Registrar por documento:

llmTokensIn, llmTokensOut, embeddingsCount.

totalCostUSD por ingest.
​

Exponer en tu UI de ROI algo como “Coste medio de ingest por documento” y “Tokens ahorrados evitando re‑indexar chunks brutos”.

Políticas:

No re‑generar perfiles si ingestionProfileVersion = 2 salvo que cambies radicalmente el pipeline o el modelo.

Añadir una opción lightIngest para docs de poco valor (solo chunks + embeddings simples, sin jerarquía) si un tenant lo quiere muy low‑cost.


Te propongo valores por defecto razonables para retrieveHierarchical y cómo ajustarlos según tamaño de documentos y contexto del modelo.

1) Parámetros clave
En tu retrieveHierarchical tienes algo así:

topKDocs: nº de documentos (profiles) que consideras.

topKSectionsPerDoc: nº de secciones por documento.

topKChunksPerSection: nº de chunks de texto por sección que realmente metes en el contexto.

Y luego en buildRagResults tienes un maxTokens total para el contexto que pasas al modelo.

2) Config recomendada para contexto ~2.000–3.000 tokens
Pensando en un modelo con ventana amplia pero queriendo mantener las respuestas rápidas y baratas:

topKDocs = 4–6

Recomiendo: 5.

topKSectionsPerDoc = 2–3

Recomiendo: 3 si las secciones están bien resumidas; 2 si son densas.

topKChunksPerSection = 2–3

Recomiendo: 2 chunks por sección (p.ej. 2 × 300–500 tokens cada uno).

Orden de magnitud:

5 docs × 3 secciones × 2 chunks = 30 chunks.

Si cada chunk tiene ~150–200 tokens tras limpieza/truncado, estás en ~4.500–6.000 tokens de contexto brutos; luego tu truncateContext corta a 2.000–3.000 tokens más relevantes.
​
​

Esto es suficiente para la mayoría de consultas técnicas sin sobrecargar al modelo.

3) Heurísticas según tamaño de documento
Puedes adaptar dinámicamente:

Si el doc es corto (sectionsCount <= 5):

topKSectionsPerDoc = min(3, sectionsCount)

topKChunksPerSection = 3 (o incluso leer la sección completa).

Si el doc es muy largo (sectionsCount > 20):

reducir a topKSectionsPerDoc = 2.

Si detectas que el usuario pregunta por algo muy específico (p.ej. incluye código de error, modelo de máquina):

aumentar topKSectionsPerDoc a 3 pero bajar topKDocs a 3–4 (más profundidad en menos docs).

Esto pueden ser decisiones heurísticas en el propio retrieveHierarchical.

4) Config por tipo de flujo
Puedes definir presets:

Assistant técnico (preguntas generales):

topKDocs = 5, topKSectionsPerDoc = 3, topKChunksPerSection = 2, maxTokens = 2500.

Agente de troubleshooting (contexto más focalizado):

topKDocs = 3, topKSectionsPerDoc = 3, topKChunksPerSection = 3, maxTokens = 2000.

Workflow que busca documentos relevantes (no necesita tanto detalle):

topKDocs = 8, topKSectionsPerDoc = 1, topKChunksPerSection = 0 (solo summary de sección).

Así mantienes controlado el contexto según uso.

5) Cómo ajustar con datos reales
Una vez en marcha, con tu sistema de evaluación:

Si contextprecision sale alta pero faithfulness baja → puede que falte profundidad: sube topKChunksPerSection.

Si contextprecision baja (mucho ruido) → reduce topKDocs o topKSectionsPerDoc.

Puedes registrar en rag_evaluations el nº real de chunks usados por respuesta y correlacionarlo con calidad vs coste.

Con esto tienes una configuración inicial razonable y un criterio claro para ajustarla con telemetría, sin tocar la interfaz de RagService

  correlationId: string,
  maxTokens: number,
): Promise<RagResult[]> {
  const fragments: RagContextFragment[] = [];

  // Opcional: incluir algún fragmento proveniente de summaryGlobal (PROFILE)
  // o summaries de sección como contexto comprimido.

  // De momento, usa chunks como base:
  for (const chunk of retrieval.chunks) {
    fragments.push({
      assetId: chunk.assetId,
      sectionId: chunk.sectionId,
      chunkId: chunk.chunkId,
      text: chunk.text,
      score: chunk.score,
      source: 'CHUNK',
      metadata: {},
    });
  }

  // Ordenar por score (desc) para priorizar contexto
  fragments.sort((a, b) => b.score - a.score);

  // Truncar por tokens
  const truncatedFragments = truncateContextByTokens(fragments, maxTokens);

  // En muchos casos puedes devolver un único RagResult con todos los fragments;
  // si tu contrato actual espera varios RagResult (por doc), puedes agrupar por assetId.
  const result: RagResult = { fragments: truncatedFragments };

  return [result];
}
truncateContextByTokens puede usar la heurística actual (contar aprox. tokens por longitud de texto) que ya tienes en el engine legacy.

4) Aplicar límites en el Context Builder
4.1 Cálculo de tokens y truncado
En buildRagResults:

ts
function approximateTokenCount(text: string): number {
  // regla rápida: ~4 caracteres por token como aproximación general
  return Math.ceil(text.length / 4);
}

function truncateContextByTokens(
  fragments: RagContextFragment[],
  maxTokens: number,
): RagContextFragment[] {
  const result: RagContextFragment[] = [];
  let usedTokens = 0;

  for (const frag of fragments) {
    const tokens = approximateTokenCount(frag.text);
    if (usedTokens + tokens > maxTokens) {
      break;
    }
    result.push(frag);
    usedTokens += tokens;
  }

  return result;
}

Te aterrizo los workflows en tu motor (estados, transiciones, nodos LLM vs humanos) de forma que puedas modelarlos en tu diseñador.

1) Workflow 1 – ORDER_ENRICHMENT
Ámbito: por orderId (pedido a fábrica).

Estados
NEW – pedido creado, sin enriquecer.

ENRICHING – Agent 1 ejecutándose.

ENRICHED – pedido enriquecido, listo para operarios.

ENRICHMENT_FAILED – error en agente (entra en retry/soporte).

Transiciones
NEW → ENRICHING

Trigger: evento “pedido confirmado” o creación de orden.

Nodo:

Tipo: LLM/agent.

Acción: para cada part del pedido:

llamar RAG (RagService.performTechnicalSearch),

llamar ORDER_ENRICHER (PromptRunner.runJson con ORDER_ENRICHER_OUTPUT).

Guarda salida en orders_enriched.

ENRICHING → ENRICHED

Condición: todos los partId han sido enriquecidos sin error.

Nodo: sistema (marca estado, dispara notificación a jefes de línea).

ENRICHING → ENRICHMENT_FAILED

Condición: error duro (p.ej. RAG sin contexto o fallo repetido).

Nodo: sistema (log + crear tarea de soporte / reintento manual).

ENRICHMENT_FAILED → ENRICHING

Trigger: reintento manual desde panel.

Nodo: sistema.

En tu diseñador, ENRICHING sería un estado con un nodo LLM asociado que itera sobre partes (o un sub‑workflow por parte).

2) Workflow 2 – ORDER_EXECUTION
Ámbito: por orderId, pero con subestado por parte partId.

Estados a nivel ORDER
READY_FOR_EXECUTION – pedido enriquecido.

IN_PROGRESS – alguna parte en ejecución.

WAITING_FOR_QUALITY_SAMPLE – todo montado, pendiente de muestreo.

QUALITY_IN_REVIEW – hay revisiones abiertas.

COMPLETED – pedido cerrado.

Subestados por PART (order_part_execution)
PENDING – parte pendiente de ejecución.

IN_PROGRESS – operario trabajando.

DONE – operario ha marcado checklist y respuestas.

UNDER_REVIEW – parte seleccionada para calidad.

APPROVED / REJECTED – resultado de calidad.

Nodos clave
2.1 Nodo “Assign Parts”
Estado: READY_FOR_EXECUTION.

Tipo: sistema / humano (jefe de línea).

Acción: asignar cada partId a un operatorId y rol (SENIOR/JUNIOR).

2.2 Nodo “Operator Assistant” (por parte)
Estado: IN_PROGRESS (parte).

Tipo: LLM/agent (Agent 2).

Input nodo:

orderId, partId, operatorId, role.

instructions de orders_enriched.

Contexto RAG (secciones de manual para esa parte).

Acción:

PromptRunner.runJson con OPERATOR_ASSISTANT → OPERATOR_ASSISTANT_UI_OUTPUT.

Devolver a la UI bloques (uiBlocks, questionsToOperator).

Nodo humano asociado:

El operario responde a questionsToOperator + marca checklist.

Esas respuestas se guardan en order_part_execution (campos tipo: followedManual, answers, timestamp).

Transición:

PENDING → IN_PROGRESS al abrir la parte.

IN_PROGRESS → DONE cuando el operario completa checklist/respuestas.

2.3 Nodo “Quality Sampling”
Estado ORDER: pasa a WAITING_FOR_QUALITY_SAMPLE cuando todas las partes están DONE.

Tipo: LLM/agent (selección) + sistema.

Acción:

Agent 3 (modo sampler simple):

seleccionar un subconjunto de partes según reglas (probabilidad x % + ponderaciones).

marcar esas partes como UNDER_REVIEW.

3) Workflow 3 – QUALITY_REVIEW
Ámbito: por orderId + partId en estado UNDER_REVIEW.

Estados por parte
UNDER_REVIEW

REVIEW_DOSSIER_GENERATED

AWAITING_INSPECTION

INSPECTED

APPROVED / REJECTED

Nodos
3.1 Nodo “Generate Review Dossier”
Estado: UNDER_REVIEW → REVIEW_DOSSIER_GENERATED.

Tipo: LLM/agent (Agent 3).

Input:

orderPart (datos de la parte del pedido).

instructions (Order Enricher).

operatorAnswers (Order Execution).

Contexto RAG (manual vigente).

Historial de no conformidades opcional.

Acción:

PromptRunner.runJson con QUALITY_REVIEWER → QUALITY_REVIEW_DOSSIER_OUTPUT.

Guardar dossier en quality_reviews (o similar).

3.2 Nodo “Physical Inspection”
Estado: REVIEW_DOSSIER_GENERATED → AWAITING_INSPECTION → INSPECTED.

Tipo: humano (revisor de calidad).

UI:

muestra summaryForReviewer, keyManualRequirements, suggestedPhysicalChecks, etc.

El revisor marca:

conforme: bool,

tipoDesviacion (NO_SIGUE_MANUAL, MANUAL_OBSOLETO, etc.),

observaciones.

Transición:

INSPECTED → APPROVED / REJECTED según entrada del revisor.

El estado ORDER pasa a:

QUALITY_IN_REVIEW si hay partes abiertas;

COMPLETED cuando todas las partes están aprobadas o gestionadas.
