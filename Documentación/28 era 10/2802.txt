Puedes implementar un “RAGAS‑like” interno con lo que ya tienes, sin librerías externas, apoyándote en tu RagJudgeService y tus colecciones de logs.

1) Qué quieres replicar de RAGAS
Ragas se centra en 4 métricas base:

Faithfulness (respuesta apoyada en contexto).

Answer Relevance (respuesta responde a la query).

Context Precision (contexto relevante para la query).

Context Recall (¿el contexto contiene lo necesario?).

Tú ya tienes las tres primeras vía RagJudgeService (faithfulness, answerrelevance, contextprecision), así que te falta sobre todo formalizar context recall y el pipeline de evaluación offline/online.
​
​

2) Dataspec interno (estilo RAGAS)
Define una estructura interna de evaluación (en BD o en código) para cada “run”:

query: texto usuario.

context: lista de chunks (texto + assetId/sectionId).

answer: respuesta generada.

groundTruthContext?: ids de chunks/secciones esperadas (para offline).

groundTruthAnswer?: respuesta ideal (si la tienes).

metrics:

faithfulness

answerRelevance

contextPrecision

contextRecall

(derivados: hallucinationScore, etc.).

Eso es exactamente lo que RAGAS modela en su dataset, pero tú lo guardas en rag_evaluations o una colección similar.
​

3) Métricas sin librerías externas
3.1 Las que ya tienes (LLM‑as‑Judge)
faithfulness, answerrelevance, contextprecision:

ya salen del prompt RAGJUDGE con JSON estable, y las guardas en tu colección de evaluaciones.
​
​

Internamente, esto es equivalente a usar los métricos LLM‑based de RAGAS (Faithfulness, Response Relevancy, LLMContextPrecision).

3.2 Context Recall (estilo RAGAS) sin librerías
Para offline, necesitas un dataset con “documentos/chunks correctos” por query.

Para cada query de tu golden set:

defines un conjunto GT de ids de doc_sections/chunks que deberían estar en el contexto (label humano o semi‑automático).

cuando tu retriever produce una lista de secciones/chunks R, calculas:

contextRecall = |GT ∩ R| / |GT|.

opcionalmente precision@K = |GT ∩ R| / |R|.

No necesitas RAGAS para esto; basta con conocer las secciones relevantes y tenerlas indexadas.

Si no quieres etiquetar manualmente:

puedes construir GT usando heurísticos: por ejemplo, para queries que vienen de un documento concreto, considerar su sección origen como “relevante” y medir si el retriever la encuentra.

4) Pipeline sin integraciones externas
4.1 Online (en producción)
Ya tienes casi todas las piezas:
​

En los flujos críticos (technical chat, análisis de entidades, agentes de planta):

con sampling (shouldSampleEvaluation), llamas a RagJudgeService.evaluateResponse.

guardas en rag_evaluations:

query, contextIds, answer, metrics, causeid, flowType, etc.

Eso te da un equivalente a RAGAS “online”, solo que tus métricas LLM‑based ya están integradas.

4.2 Offline (pre‑deploy / comparaciones)
Inspirado en RAGAS pero sin usarlo:

Curar un golden dataset interno:

Lista de queries reales (de técnicos).

Para cada una, uno o varios documentos/secciones “gold” (GT).

Opcional: respuestas ideales (si quieres medir exactitud, no solo RAG).

Script interno de evaluación:

Para cada query:

Ejecutar tu pipeline RAG (v1, v2, variantes).

Guardar: retrieved context ids + answer.

Calcular offline:

contextRecall/precision con GT.

Llamar a RagJudgeService.evaluateResponse (offline, sin afectar a usuarios) para obtener faithfulness/answerrelevance/contextprecision.

Guardar resultados en una colección rag_offline_experiments con:

experimentId, variant (engine v1, v2…),

métricas agregadas por variante.

Con esto, tienes un clon funcional de RAGAS sin depender de su SDK: dataset + métricas de retrieval + métricas LLM‑judge, todo en tu stack.

5) Cómo integrarlo con lo que ya tienes
RagJudgeService + ragevaluations → métricas tipo RAGAS (faithfulness, answer relevance, context precision).
​
​

Tu diseño de golden set puede guardarse como colección rag_golden_sets (queries + groundTruthContext/Answer).

El “runner offline” puede ser un use case tipo EvaluateRagVariantUseCase que:

usa RagService.performTechnicalSearch con distintos flags/params,

usa RagJudgeService,

calcula recall/precision y guarda en rag_offline_experiments.

No necesitas ninguna integración externa ni RAGAS como servicio; solo replicar los conceptos con tu propio LLM y tus propias colecciones.

# AI Governance – Diseño de Flujos RAG

Checklist para revisar ANTES de crear o activar un flujo RAG (workflows, agentes, endpoints).

## 1. Alcance funcional

- [ ] El flujo tiene un **objetivo claro** (p.ej. enriquecer pedido, responder dudas técnicas, revisar calidad).
- [ ] Están identificadas las **entidades/documentos** que puede tocar:
  - [ ] `entitySlug` definidos (ej. `entities`, `cases`, `knowledgeassets`).
  - [ ] Spaces / tags / scopes de documentos acotados.
- [ ] Las **acciones permitidas** están listadas:
  - [ ] Solo lectura (RAG, análisis).
  - [ ] Escritura: `updateentity`, cambios de estado.
  - [ ] Generación de tareas humanas.
  - [ ] Notificaciones / logs.

## 2. Prompts y modelos

- [ ] Todos los prompts usados están **registrados en `PromptService`** (nada inline).
- [ ] Cada prompt tiene:
  - [ ] Descripción funcional.
  - [ ] Schema de salida claro (Zod u otro).
  - [ ] Ejemplos de uso (few-shot si aplica).
- [ ] Los modelos LLM y embeddings se seleccionan vía:
  - [ ] `TenantConfig` / `AIMODELIDS`.
  - [ ] Nunca hard-coded en el flujo.
- [ ] Se ha definido:
  - [ ] Temperatura y parámetros clave (topK, maxTokens, etc.).
  - [ ] Límites de tokens razonables para evitar desbordes.

## 3. Seguridad de datos

- [ ] La ingest de documentos sensibles usa `maskPii` por defecto.
- [ ] No se exponen datos fuera del tenant:
  - [ ] CrossVerticalEngine está desactivado salvo opt-in explícito.
  - [ ] No se usan identificadores clientes/tenants en prompts de compartición.
- [ ] Se han revisado:
  - [ ] Campos que deben ir cifrados.
  - [ ] Políticas de retención de logs (application logs, ai audit logs).

## 4. Controles de gobernanza

- [ ] Acceso a endpoints controlado por `Guardian` / `enforcePermission`:
  - [ ] Recursos y acciones bien definidos (ej. `technicalanalysis:read`, `entities:write`).
- [ ] Para acciones de escritura:
  - [ ] Se usa `GovernanceEngine.evaluateAction` antes de actualizar entidades.
  - [ ] Se ha decidido para cada acción si:
    - [ ] `autoExecute = true` (riesgo bajo).
    - [ ] `requiresReview = true` (riesgo medio/alto).
- [ ] Las acciones con `requiresReview`:
  - [ ] Generan tareas humanas mediante `HumanTaskHandler`.
  - [ ] No modifican datos automáticamente.

## 5. Límites de uso y costes

- [ ] Definidos límites por tenant en `UsageRepository` / `AccessControlService`:
  - [ ] Nº de consultas RAG.
  - [ ] Nº de informes generados.
  - [ ] Cotas para análisis largos (agentic graphs).
- [ ] El flujo registra consumo:
  - [ ] `UsageService.trackUsage` o `trackLLM` en puntos clave.
- [ ] Se han definido SLAs:
  - [ ] Latencia objetivo por flujo (P95).
  - [ ] Timeouts máximos aceptables.

## 6. Evaluación y calidad

- [ ] El flujo está preparado para evaluación con `RagJudgeService`:
  - [ ] Se capturan `query`, `answer`, `context`.
  - [ ] Se guardan métricas de `faithfulness`, `answerRelevance`, `contextPrecision`.
- [ ] Se ha definido un **plan de golden set** (si aplica):
  - [ ] Conjunto de queries de prueba.
  - [ ] Respuestas o contextos esperados.
- [ ] Hay criterios de éxito mínimos:
  - [ ] Faithfulness medio ≥ X.
  - [ ] Answer Relevance medio ≥ Y.

# AI Quality & RAG Evaluation Playbook

Guía interna para diseñar, ejecutar e interpretar evaluaciones de calidad RAG (tipo RAGAS) usando solo nuestra propia infraestructura.

---

## 1. Objetivos de la evaluación

- Medir si las respuestas:
  - [ ] Son **fieles** al contexto (sin alucinaciones).
  - [ ] Responden realmente a la **pregunta**.
  - [ ] Usan **contexto relevante** (sin ruido).
- Medir si el **retriever**:
  - [ ] Recupera las secciones/chunks correctos.
  - [ ] Evita traer contenido irrelevante.

---

## 2. Conceptos clave y métricas

Métricas basadas en LLM Judge (inspiradas en RAGAS):

- **Faithfulness**  
  - ¿La respuesta se puede derivar de los trozos de contexto proporcionados?  
  - Valores típicos: 0–1.

- **Answer Relevance**  
  - ¿La respuesta contesta a la intención de la consulta?  
  - Valores típicos: 0–1.

- **Context Precision**  
  - ¿Qué porcentaje del contexto mostrado es realmente relevante para la pregunta?  
  - Valores típicos: 0–1.

Métricas de recuperación (offline):

- **Context Recall**  
  - Proporción de chunks/secciones relevantes que han sido recuperadas.
  - `recall = |GT ∩ R| / |GT|` (GT = ground truth, R = recuperados).

- **Context Precision (retrieval)**  
  - Proporción de chunks recuperados que son relevantes.
  - `precision = |GT ∩ R| / |R|`.

---

## 3. Dataset de evaluación (Golden Set)

### 3.1 Tipos de golden sets

- **Golden set por documento/sección**  
  - Queries derivadas directamente de secciones de manuales, con:
    - [ ] Lista de secciones/chunks que deberían responder (GT).
    - [ ] Respuesta ideal opcional.

- **Golden set por flujo de negocio**  
  - Queries reales de técnicos/operarios, clasificadas por:
    - [ ] Tipo de flujo (chat técnico, análisis de entidad, asistente de pedido).
    - [ ] Nivel de criticidad (baja/media/alta).

### 3.2 Estructura sugerida (colección `rag_golden_sets`)

- `tenantId`
- `flowType` (ej. `TECHNICAL_CHAT`, `ORDER_ANALYSIS`)
- `query`
- `groundTruthContextIds` (ids de doc_sections/chunks)
- `groundTruthAnswer` (opcional)
- `tags` (ej. `safety`, `electrical`, `maintenance`)
- `createdBy`, `createdAt`

---

## 4. Evaluación online (producción)

### 4.1 Cuándo evaluar

- Flujos críticos:
  - [ ] Chat técnico para manuales.
  - [ ] Análisis de entidades técnicas.
  - [ ] Agentes que proponen cambios de datos.

- Sampling:
  - [ ] Evaluar solo una fracción de las peticiones (p.ej. 5–10%).
  - [ ] Ajustable por tenant/flujo.

### 4.2 Cómo se hace

- Para una petición RAG real:
  - [ ] Capturar `query`, `answer`, `context` (ids de chunks/sections).
  - [ ] Llamar a `RagJudgeService` con esos datos.
  - [ ] Guardar en colección `rag_evaluations`:
    - Métricas de LLM (faithfulness, answerRelevance, contextPrecision).
    - Metadatos: flujo, agente, tenant, timestamps.

### 4.3 Uso de los resultados

- Monitorizar:
  - [ ] Tendencias por flujo/agente.
  - [ ] Casos de baja faithfulness repetidos.
- Acciones:
  - [ ] Ajustar prompts.
  - [ ] Cambiar parámetros de RAG (topK, filtros).
  - [ ] Aumentar supervisión humana (governance, human tasks).

---

## 5. Evaluación offline (experimentos)

### 5.1 Objetivo

- Comparar variantes:
  - [ ] RAG v1 vs RAG v2.
  - [ ] Distintos modelos de embedding.
  - [ ] Diferentes estrategias de chunking.
  - [ ] Variaciones de prompts.

### 5.2 Proceso general

1. Seleccionar un golden set (colección `rag_golden_sets`).
2. Definir variantes de configuración (engine/version/params).
3. Para cada query:
   - [ ] Ejecutar la variante.
   - [ ] Registrar:
     - Contexto recuperado (ids).
     - Respuesta generada.
     - Métricas LLM (vía `RagJudgeService`).
     - Métricas de retrieval (recall/precision contra GT).
4. Guardar resultados en `rag_offline_experiments`:
   - `experimentId`, `variantId`, `metricsAgg`, `perQueryResults`.

### 5.3 Interpretación

- Comparar por variante:
  - [ ] Faithfulness media.
  - [ ] Answer Relevance media.
  - [ ] Context Precision media.
  - [ ] Context Recall/Precision (retrieval).

- Criterios típicos:
  - [ ] Aceptar variante si:
    - no baja faithfulness,
    - mejora recall y/o answerRelevance,
    - no dispara el coste ni la latencia.

---

## 6. Criterios de aceptación para ir a producción

### 6.1 Por flujo

Antes de activar una nueva versión o configuración:

- [ ] Faithfulness medio ≥ umbral (p.ej. 0.85).
- [ ] Answer Relevance medio ≥ umbral (p.ej. 0.85).
- [ ] Context Precision ≥ umbral (p.ej. 0.7).
- [ ] Context Recall ≥ umbral (p.ej. 0.7) para el golden set relevante.
- [ ] Latencia dentro de SLA definido.
- [ ] Coste estimado aceptable.

### 6.2 Por tenant / entorno

- [ ] Cambios probados primero en `STAGE` con datos de prueba.
- [ ] Para `PRODUCTION`:
  - Sampling de evaluación ajustado a un valor bajo inicial.
  - Follow-up de métricas durante X días.

---

## 7. Roles y responsabilidades

- **AI Platform Owner**
  - Define métricas/umbrales globales.
  - Decide variantes de engine y configuración.

- **Owner del flujo (product/ops)**
  - Define golden set funcional.
  - Valida que las respuestas son útiles para el caso de uso.

- **Ingeniería**
  - Implementa cambios de config/prompts.
  - Mantiene scripts y pipelines de evaluación offline.

---

## 8. Checklist rápido para nuevos cambios RAG

Antes de desplegar una nueva versión/configuración:

- [ ] Existe un golden set relevante.
- [ ] Se ha ejecutado al menos un experimento offline comparando variantes.
- [ ] Los resultados cumplen los criterios de aceptación.
- [ ] Hay plan de rollback claro (cómo volver a versión anterior de engine/prompt).
- [ ] El sampling online está configurado y monitorizado.
- [ ] El equipo de negocio está informado del cambio y de cómo interpretar las métricas.

1) Contrato TypeScript estable para RagJudgeService
1.1 Tipos base
ts
// Identifica fuente de la evaluación
export type RagEvalMode = 'ONLINE' | 'OFFLINE_EXPERIMENT';

// Qué vamos a evaluar
export interface RagEvaluationInput {
  tenantId: string;
  flowType: string;          // 'TECHNICAL_CHAT' | 'ENTITY_ANALYSIS' | ...
  agentKey: string;          // identificador lógico del agente/workflow
  engineVersion: string;     // 'RAG_V1' | 'RAG_V2_HIERARCHICAL' | ...
  query: string;
  answer: string;
  contextTexts: string[];    // textos que vio el modelo
  contextIds: string[];      // ids de chunks/sections, en mismo orden que contextTexts
  mode: RagEvalMode;
  correlationId?: string;
  // opcionales
  criticality?: 'LOW' | 'MEDIUM' | 'HIGH';
  metadata?: Record<string, any>; // ej. pedidoId, entityId...
}

// Resultado “estable” que usarán BD y dashboards
export interface RagEvaluationMetrics {
  faithfulness: number;            // 0–1
  answerRelevance: number;         // 0–1
  contextPrecisionLLM: number;     // 0–1
  hallucinationScore?: number;     // opcional, 0–1
  reasoningSummary?: string;       // texto breve opcional (para debug)
}

export interface RagEvaluationOutput {
  input: RagEvaluationInput;
  metrics: RagEvaluationMetrics;
  llmModel: string;                // modelo del judge
  createdAt: Date;
}
1.2 Interfaz de servicio
ts
export interface IRagJudgeService {
  // Evalúa respuesta + contexto, sin efectos laterales
  evaluate(input: RagEvaluationInput): Promise<RagEvaluationOutput>;
}
1.3 Wrapper para persistencia/logging
Define un “orquestador” que use el judge y persista en las colecciones que definimos:

ts
export interface RagEvaluationPersister {
  saveOnlineEval(output: RagEvaluationOutput): Promise<void>;
  saveOfflineExperimentResult(
    experimentId: string,
    variant: string,
    goldenId: string,
    retrievalMetrics?: {
      contextRecall?: number;
      contextPrecisionRetrieval?: number;
    }
  ): Promise<void>;
}

export class RagEvaluationOrchestrator {
  constructor(
    private judge: IRagJudgeService,
    private persister: RagEvaluationPersister
  ) {}

  async evaluateOnline(input: RagEvaluationInput) {
    const out = await this.judge.evaluate({ ...input, mode: 'ONLINE' });
    await this.persister.saveOnlineEval(out);
    return out;
  }

  async evaluateOfflineExperiment(params: {
    input: RagEvaluationInput;
    experimentId: string;
    variant: string;
    goldenId: string;
    retrievalMetrics?: {
      contextRecall?: number;
      contextPrecisionRetrieval?: number;
    };
  }) {
    const out = await this.judge.evaluate({
      ...params.input,
      mode: 'OFFLINE_EXPERIMENT',
    });
    await this.persister.saveOfflineExperimentResult(
      params.experimentId,
      params.variant,
      params.goldenId,
      params.retrievalMetrics
    );
    return out;
  }
}
Con esto, el resto del código solo habla en términos de RagEvaluationInput/Output, y el juez puede cambiar internamente (prompt, modelo) sin romper el contrato.

2) Versionado/migraciones de schemas
Mantén los schemas evolutivos con un par de reglas simples:

rag_evaluations:

No borres campos; solo añade nuevos como opcionales.

Añade un campo schemaVersion?: number si prevés cambios fuertes en el futuro.

Si cambias la semántica de una métrica (p.ej. redefinir contextPrecisionLLM), sube schemaVersion y trata los datos antiguos en dashboard con cuidado (ej. filtrar por versión).

rag_offline_experiments y _results:

Igual: añade schemaVersion?: number a resultados por si cambias la definición de métricas.

Si un experimento usa una métrica nueva, puedes dejarla null en experimentos antiguos.

Migraciones prácticas:

Evita migraciones “en masa” de colecciones grandes; asume que dashboards pueden convivir con campos nulos.

Solo migra cuando:

cambias claves primarias (tenantId, flowType, etc.),

o quieres backfill de datos derivados (p.ej. criticality calculada).

En tu caso, con el diseño actual, puedes arrancar sin schemaVersion y añadirlo cuando tengas una primera versión estable en producción.

3) Conexión con GovernanceEngine y políticas
La conexión clave es: usar las métricas de evaluación como señales para gobierno, sin acoplar fuerte los componentes.

Puntos de integración:

En decisiones de workflows (BranchHandler):

Usa confidenceScore +, cuando exista, métricas recientes de rag_evaluations para ese flujo/agentKey:

si el flujo tiene media de faithfulness baja en la última ventana, podrías forzar requiresReview en Governance para ese agente.

En GovernanceEngine.evaluateAction:

Puedes extender la lógica de políticas para aceptar condiciones tipo:

“si agentKey=X y faithfulnessMean < 0.8 → canExecute=false o requiresReview=true”.

La evaluación la haces consultando un pequeño “cache” de métricas agregadas (no en caliente en cada llamada a DB para no penalizar).

En aipolicies:

Añadir campos que codifiquen dependencias con calidad:

minFaithfulness?: number

minAnswerRelevance?: number

GovernanceEngine puede consultar estos valores y, junto con las métricas actuales, decidir si permitir auto‑execute o forzar revisión humana.

Con este patrón, RAGJudge + rag_evaluations se convierten en fuente de señales y GovernanceEngine es quien decide el comportamiento de los workflows, sin que ninguno de los dos se acople al detalle interno del otro.

si latestQualityStats.faithfulnessMean < minFaithfulness → canExecute=false, requiresReview=true.

si currentConfidenceScore < minConfidenceScore → igual.

Registrar decisión en aiauditlogs.

latestQualityStats lo obtienes de un servicio ligero que cachea agregados de rag_evaluations (siguiente sección).

Puedes tener otra política más estricta para safety:

2) Cómo calcular y cachear medias por flujo/agentKey
Objetivo: que GovernanceEngine pueda ver rápidamente “cómo va” un agente sin ejecutar agregaciones pesadas en cada decisión.

2.1 Servicio de estadísticas de calidad
Define algo tipo:

ts
export interface AgentQualityStats {
  tenantId: string;
  agentKey: string;
  flowType: string;
  window: '1d' | '7d' | '30d';
  faithfulnessMean: number;
  answerRelevanceMean: number;
  contextPrecisionLLMMean: number;
  samples: number;
  updatedAt: Date;
}

export interface IAgentQualityStatsRepository {
  getStats(
    tenantId: string,
    agentKey: string,
    flowType: string,
    window: '1d' | '7d'
  ): Promise<AgentQualityStats | null>;

  saveStats(stats: AgentQualityStats): Promise<void>;
}
Colección sugerida: rag_agent_quality_stats.

2.2 Job periódico (cron / worker)
Cada X minutos (p.ej. cada 5 o 15):

Para cada tenantId + agentKey + flowType relevante:

Lanzar una agregación sobre rag_evaluations en ventana móvil (p.ej. últimos 7 días):

js
db.rag_evaluations.aggregate([
  {
    $match: {
      tenantId,
      agentKey,
      flowType,
      createdAt: { $gte: new Date(Date.now() - 7 * 24 * 60 * 60 * 1000) },
    },
  },
  {
    $group: {
      _id: null,
      samples: { $sum: 1 },
      faithfulnessMean: { $avg: '$metrics.faithfulness' },
      answerRelevanceMean: { $avg: '$metrics.answerRelevance' },
      contextPrecisionLLMMean: { $avg: '$metrics.contextPrecisionLLM' },
    },
  },
]);
Guardar/actualizar un doc en rag_agent_quality_stats:

text
{
  "tenantId": "DEMO_ELEVATORS",
  "agentKey": "ORDER_ASSISTANT",
  "flowType": "ORDER_ANALYSIS",
  "window": "7d",
  "samples": 123,
  "faithfulnessMean": 0.91,
  "answerRelevanceMean": 0.89,
  "contextPrecisionLLMMean": 0.78,
  "updatedAt": ISODate("2026-03-07T15:10:00Z")
}
Índice recomendado:

{ tenantId: 1, agentKey: 1, flowType: 1, window: 1 }

2.3 Uso desde GovernanceEngine
Cuando GovernanceEngine.evaluateAction se ejecuta:

Recupera AgentQualityStats para (tenantId, agentKey, flowType, '7d').

Si no hay stats (nuevo agente), aplicar política por defecto o forzar requiresReview.

Compara con los umbrales de la acción (como en el ejemplo de políticas).

Esto mantiene la decisión barata: un findOne por acción, no un aggregate cada vez.

Un ejemplo claro de cómo codificar políticas dependientes de calidad.
